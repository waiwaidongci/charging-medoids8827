# 公交充电曲线分群

滨江市公交能源调度组，负责 3 个停车场的 180 辆纯电公交及其夜间补能。。场站充电平台按会话导出起充后的功率点。分析员（analyst）导入和运行分群，复核员（reviewer）核对离群会话、审批班报，值班长（viewer）在结果页和交班报告中查看已发布结论。此前分析员在 Excel 中按峰值排序，再打开曲线逐条比对。

充电平台导出的 CSV，每行记录一辆车在一次会话中的一个功率采样点。会话编号在批次内唯一，起充时间采用场站本地时间 YYYY-MM-DD HH:MM。只导出起充后 0 至 35 分钟每 5 分钟一个点，功率范围为 0 至 600 kW。 向能源调度、场站值班长和桩机维保班交付逐会话归属表、实测中心曲线、各群平均及最大 DTW、完整性问题及待核对清单。

- 按峰值排序会把高功率维持型与快速降功率型混在一起，夜班需要逐条打开曲线区分。
- 遥测重发会留下同一时点的两条记录，缺采也容易被 Excel 折线连起来，整理后的表格难以辨认原始问题。
- 交班时只留下人工分组结果，维保人员找不到代表曲线，也难以判断某条会话为何归入该组。

## 六个业务模块

1. 夜充调度总览
2. 起充采样台账
3. 曲线分群配置
4. 实测中心与归属
5. 夜充结论复核
6. 充电班报分发

## 工作剧本

1. 2026 年 11 月 24 日 04:50，滨江公交夜班分析员查看总览，确认东桥场和南环场共有 12 条补能会话待复核。
2. 05:00，分析员导入 2026-11-24_滨江公交夜班充电采样.csv。首条会话 C1124-01 于 00:05 起充，12 条会话共 96 个功率点。
3. 05:10，在分群配置中选择 3 群、1 个采样格带宽，允许同类功率变化在 5 分钟以内对齐。
4. 05:15，分析员查看分群明细。实测中心是 C1124-02、C1124-07、C1124-11，三群各 4 条会话。
5. 05:20，复核员打开 C1124-01，核对到所属中心的累计功率差 33 kW 和到次近中心的 357 kW，再抽查第三群最大距离对应的 C1124-09。
6. 05:25，复核员确认 12 条会话都满足 8 个唯一采样点，批准分群班报。若 C1124-09 缺少 15 分钟点，先联系东桥场的采集值班人员核对源记录，再重跑复核。
7. 05:30，分析员导出会话归属和组内离散度，安排发给夜班能源调度，供 06:00 早班交接使用。

## 算法与复核

在固定采样网格上，用带宽受限的动态时间规整累加绝对功率差，保留功率尺度。PAM 确定性选取实测会话作为中心，逐次执行使总距离降幅最大的单中心交换。每条会话列出最近与次近中心及其距离差。

采样缺点、重复或偏离网格的会话退出分群并留在复核表，整批暂缓发布。完整会话数不足时，补齐采样或降低分群数后再运行。会话标识冲突、时间格式或功率无效时，修正源 CSV 后重导。 复核问题为「这批会话的采样点是否齐全？各组中心曲线、组内离散度和归属依据是否足以支持早班交接？」。每次分析绑定数据版本和参数，原始数据按规范化内容的 SHA-256 去重。日程针对已复核的固定结果版本，每日模式按初次投递时间每 24 小时重复。停机期间错过多次时只补一份到站内收件箱，下一次回到原时间点。

| 字段 | 含义 | 类型 |
|---|---|---|
| `session_id` | 充电会话编号 | str |
| `bus_id` | 车辆编号 | str |
| `depot` | 停车场站 | str |
| `started_at` | 本地起充时间 | str |
| `minute_offset` | 起充后分钟 | int |
| `power_kw` | 实测充电功率（kW） | float |

## 启动

```sh
[ -f .env ] || cp .env.example .env
docker compose up -d --build --wait
docker compose exec -T backend python -m scripts.seed_demo
```

- Web 界面 `http://127.0.0.1:18295`
- API 文档 `http://127.0.0.1:19295/docs`
- 数据库端口 `17795`

| 账号 | 演示密码 | 工作权限 |
|---|---|---|
| analyst | analyst-demo-24 | 导入 CSV、运行分析、导出工作稿 |
| reviewer | reviewer-demo-24 | 复核、设置和停止投递、导出 |
| viewer | viewer-demo-24 | 浏览结果、导出已批准的报告、查收投递 |

原生 HTML/CSS/JavaScript 前端与 Nginx、FastAPI、Python worker、MySQL 8.0 和 Redis 组成五服务 Compose。`backend/src/services/domain.py` 存放业务算法，`domain.json` 定义字段与验收口径，`frontend/src/pages` 为业务页面。更新任一侧源文件后，用 `docker compose up -d --build` 重建对应镜像。`backend/src/constants/enums.py` 和 `frontend/src/constants/enums.js` 定义角色及运行状态。`.env` 支持前端、API、数据库端口、演示 seed 开关和 JWT 密钥。首次部署到非演示环境时更换演示身份及 JWT/数据库凭据。

`docker compose down` 停止服务并保留数据卷。现场数据和演示结果可以在各自版本中并存。
